## 保存の仕組みを増やさないための組込み方

独立したイベントphase、eventSeen、イベント予約/使用済みフラグは増やさない。**指定の戦闘後の報酬1回を、小イベントの「HPを払って既存札を受け取る／受け取らない」2択へ置き換える**案とする。通常報酬に追加でもう1枚配る案ではない。6戦の戦闘数や支度の休息/進化/除去は維持する。

これは通常4択を一部減らす取引であり、3案を一度に入れると適応の材料を固定しすぎる。最初は第2戦後1か所だけ。4択を必ず保持したまま独立した追加イベントを挟む仕様は、この案では満たさない。その仕様なら二重解決防止の状態管理を別設計する必要がある。

### 保存・復帰に使う既存項目

| 既存項目 | 使い方 |
|---|---|
| `phase: reward` / `battle` | どの固定イベントかを決める。固定位置でランダムイベント抽選をしない |
| `rewardOffers` | イベントの受取り札1枚だけを格納。例 `[charge]`。Bは既存のnull（取らない）入力で表す |

| 既存の遷移先 | 第2/4戦後はsanctuary、第5戦後はcampへ。phaseが変わるので再解決できない |

**互換条件:** 対象はdotが確定した新ルールの新しい報酬だけ。新ルールのversion/ruleset名は未確認なのでここで番号を決めない。既存のruleset等の識別を使い、旧classic/旧growth-v1の未開封報酬も含め変更しない。旧24枚モードは対象外。開いていた4候補は、新旧ともこのイベントへ変換しない。

新ルールがまだ区別できない状態で公開growth-v1へ差し込まない。独立イベント用の新保存形式を作らずとも、どのランに新ルールを適用するかは必要。この条件はdotの基本札変更の統合仕様と合わせる。

## 共通の料金と2択表示

選択前の現在HPをh、最大HPをMとし、通常報酬の共通回復後HPを **H = min(M, h+8)** とする。確認前の画面には現在HPと、A/Bそれぞれの**確定後HP**を示す。

- A: 料金pをHから払って、示した通常カード1枚を取得。確定後HPはH−p。
- B: 料金0、追加カードなし。確定後HPはH。通常の戦闘後回復は両方同じで、イベント固有の回復ではない。
- AはH>pの場合だけ可。先にhから料金を引いてから回復すると満HPで料金が消えるため、**回復を上限で切った後に料金を引く**。
- 1回の確定操作で回復・支払・取得・phase遷移をまとめる。カード選択だけで取得/支払しない。失敗は完全無変更。
- A/Bの2ボタンが決着の選択。別の「今回は取らない」はBにまとめ、3択にしない。閉じる/戻るは未確定のままで決着には数えない。

以下のHは共通回復後の値。例えば現在HP4ならH12、現在HP52以上ならH60（M60）。到達頻度や料金の適正はまだ未検証。

## 1. 封じた雷瓶（先行案）

第2戦後の報酬1回。まだ休息/進化/除去はその次に通常どおり選べる。

> 誰かの残した雷瓶。少しの命を灯せば、一戦に一度の魔力へ変えられる。

| 選択 | 数値/取得物 | 次に役立つ条件 |
|---|---|---|
| A：HP3を払い、蓄電を受け取る | H−3、通常 `charge` 1枚。0コスト、魔力+1（上限5）、消滅 | 2/3コスト攻撃を使いたい、枯渇後の資源を戻したい、灰の守り/灰読みの先行消滅が必要 |
| B：封を開かず通る | H、追加札なし | HPが心細い、基本札主体で魔力が余る、既に蓄電があり薄いデッキを保ちたい |

- H60ならA57/B60。H12ならA9/B12。無料基本札中心で魔力を余らせる構成では3HPとデッキ1枚を払う価値が低い。
- 例: 次戦初手魔力2、雷撃と瓶由来の蓄電がある。蓄電→魔力3→雷撃2で残1。蓄電がなければ雷撃後0。これは火力増加ではなく、後続1コスト行動/持越しの余裕。
- 火花を使い切り条件で強めたいなら、先に蓄電すると条件を外すこともある。常に最初に使う札にはしない。
- +3候補では魔力生成の希少性は下がる一方、基本札も有料で支払い用途は増える。1HP相当の利益などとは換算せず別試遊する。
- 先行理由: 新状態・新カード・新効果が不要。料金1項目と、取得/見送りの遷移を確かめればよく、支度の休息/進化/除去を上書きしない。

## 実装箇所と最小の新処理（採用後の担当作業）

| 場所 | 再利用/追加すること |
|---|---|
| `planning-engine.js / openReward` | 対象の新ルール・指定battleだけ既存rewardOffersへ1候補をセット。固定イベントなのでRNG追加なし。他の報酬は現在の抽選を保持 |
| `chooseReward` | 対応する1候補が保存済みなら価格を決定。Hを計算、H>料金を確認、既存のdeck/rewards/lastReward更新と料金支払・phase遷移を一度に行う。B/nullも通常の遷移。料金を受け入れたという未保存のUI変数を唯一の根拠にしない |
| `planning-game.js / storyContent` | 対象ルール、battle、保存済みrewardOffersがイベントの1候補と一致する時だけA/B表示。通常の4択画面は維持。HP予測、通常札全文、受取り/通過を表示 |
| `restoreSave` | 既存配列は長さ4以下を許しているが「1候補だから無条件にイベント」としない。対象ルール・位置・札の整合性を確認。不正な組合せは拒否。schema/field追加はしない |
| 既存save処理 | 1回の確定後に通常の保存を呼ぶ。イベント専用キー・ログを唯一の使用済み根拠にする仕組みは作らない |

既存のカード取得処理を使えるが、HP料金と2択表示は**新しい処理**。現在のchooseRewardがそのまま有料取引を実行できる、と誤認しない。

### 途中で閉じた場合

| 閉じる時点 | 再開時の扱い |
|---|---|
| 勝利、報酬を開く前 | victoryのまま。対象の新ルールなら初めてopenRewardした時に固定候補を保存する |
| A/Bを見ているが未確定 | rewardのまま。同じ1候補・料金・HP予測を再表示。支払/取得なし。HPの通常回復8もまだ確定しない |
| A確定・通常保存済み | sanctuary/campへ。料金・カード取得・回復を再実行しない |
| B確定・通常保存済み | sanctuary/campへ。通過済みで追加札なし。再度選べない |
| 保存書込み失敗後に終了 | 端末に残る最後の成功保存から再開。状態の永続化を保証したと表示しない。確定前保存なら料金/札とも未取得へ戻る。半分だけ保存する構造を避ける |

## 試験項目と採否

1. イベント前HP1/4/52/60、最大HP60/66、H計算、満HPでも3/4/5の料金が消えない。通常回復8は1回だけ。HP0にする支払いは不可。
2. Aは通常ID1個だけを追加、rewards/lastReward/デッキ多重集合が一致。Bは追加しない。次戦初手への実物移動、同名重複、取得後の進化/除去が現在の仕組みどおり。
3. 開封前/未確定/確定後/支度/次戦で保存復帰、同じ次操作/RNGが一致。連打・古いボタン・phase不一致で二重支払/二重取得をしない。
4. 既に開いている4択、旧classic/growth-v1、旧v1/v2移行、旧24枚版は変更なし。新形式の判別と外側ラッパーをdotの確定仕様へ合わせる。未知形式をイベント用に通すvalidator緩和はしない。
5. 固定イベント以外の通常報酬は候補/抽選/RNGを保持。ただし新ルールのイベントで通常shuffleを省けば、その後の新ルール内RNG経路は以前の通常報酬版と変わる。ラン全体のRNG同一を保証せず、**同じ確定後保存からの復帰一致**を保証する。
6. スマホ横画面でA/B、料金、確定後HP、取得札、戻るが読める。料金支払いで得るものを回復/進化と誤解しない。
7. 封じた雷瓶だけを、通常報酬版と同じseed/護符/HP/デッキ条件で比較。取得/通過、瓶の実使用、上限で失う魔力、消滅コンボ、HP被害、カード使用操作数、次戦/ランの結果を記録。HP高/低・魔力を使う/余らせるデッキを分ける。

**採否:** 封じた雷瓶が毎回取得され、HPやデッキで選択が変わらなければ採用しない。料金だけを増やして罰にせず、通常4択を失った影響も見る。3案ともHPと既存札の交換に寄せたのは保存/実装範囲を小さくするためであり、イベントの種類を増やしたこと自体を面白さの成果と扱わない。
